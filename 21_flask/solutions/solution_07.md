# Solution 07 — Text from outside, syntax on the inside

**a) What the three have in common**

**A value from outside was concatenated into a string that a parser then reads as
code, so the boundary between what you wrote and what somebody sent you stopped
existing.**

That sentence covers all three without adjustment. In the SQL case the parser is
SQLite and the code is a `WHERE` clause; in the two HTML cases the parser is the
browser and the code is markup and JavaScript. The mechanism is identical: text
crossed from the data side to the instruction side because it was **pasted in** rather
than **passed in**.

The one fix, and it is the same fix: **send the value separately from the text.**

- SQL: a placeholder — `execute("... WHERE tag = ?", (tag,))`. The query is compiled
  first; the value arrives afterwards, into a slot.
- HTML: a template variable — `{{ text }}` with `text=comment`. The template is parsed
  first; the value arrives afterwards, escaped on the way in.

Both work for the same reason: **by the time the value arrives, the parsing has already
happened**, so there is no point at which it could become syntax. That is why the fix
is complete rather than best-effort, and why "escape it carefully" is a different and
worse kind of answer (module 19, exercise 07).

**b) Why escaping-by-default is the right way round**

Because of which mistake requires typing something extra.

With escaping by default, forgetting to think produces **an ugly page** — markup
showing as text where you wanted a link. You see it immediately, in the browser, and
you fix it by adding `|safe` where you meant to. The failure is visible and harmless.

With the other default, forgetting to think produces **a working exploit**, on the one
field somebody eventually pastes a script into. The failure is invisible and permanent,
and it is invisible precisely because nothing looks wrong.

So: the default should make the safe case free and the dangerous case deliberate. What
the other way round would cost is exactly what old template systems cost, and what PHP
spent fifteen years being famous for — a whole class of vulnerability that exists
because the easy thing was the unsafe thing.

**c) Why the f-string is just as unsafe**

Because escaping is not a property of `|safe` — it is a property of **the template
engine having looked at the value**. An f-string is evaluated by Python, which has no
idea it is building HTML. `comment` goes in exactly as it arrived.

So `f"<p>{comment}</p>"` is not "`|safe` minus the marker". It is `|safe` applied to
every interpolation, silently, with no marker to grep for and nothing in the line
saying that a decision was made.

What that implies about building HTML in Python: **do not**, except through something
that knows it is HTML. That is not a style preference — it is the observation that the
escaping has to happen at the point where the value meets the markup, and only the
template engine is at that point. `markupsafe.escape()` by hand is the same idea done
manually, with the same "somebody has to remember" problem as SQL escaping.

The practical rule: HTML is produced by templates. A view function returns data or a
rendered template, never a string it assembled.

**d) A legitimate `|safe`**

Rendering markup **your own program produced**. The usual case is a Markdown field:
the author writes Markdown, a library converts it to HTML on the server, and the
result has to reach the page as markup or the whole feature does nothing.

```python
html = markdown.markdown(article.body)      # produced here, from a known input
return render_template("article.html", body=html)   # {{ body|safe }}
```

What has to be true for that to be legitimate:

1. **The HTML was generated by code you control**, not supplied by a user.
2. **The generator sanitises** — Markdown converters happily pass raw `<script>`
   through unless told not to, so this needs `bleach` or an equivalent, with an
   allow-list of tags. Without that step, `|safe` on rendered Markdown is the original
   bug wearing a hat.
3. **The trust is documented at the source.** The value should be marked safe where it
   is created, not where it is displayed — `markupsafe.Markup(...)` on the way out of
   the converter, so the template does not have to opt out at all.

Point 3 is the general principle: **mark trust where the knowledge is.** The template
does not know where its variables came from; the function that made them does.
